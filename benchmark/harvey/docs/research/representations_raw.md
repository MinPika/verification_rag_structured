# Research Report: Offline Corpus Representation for Law-Firm DMS Agents (Harvey LAB "firm-knowledge")

## 0. Grounding: what the source material says

Harvey's blog (fetched directly) confirms the exact setup: Calderwood & Harkness has 266 matters, 46 clients, 15 practice areas, 9,288 files, 108M tokens, 250 tasks graded by LLM judge against atomic rubric criteria. Key diagnosis: *"Failures are largely explicable by an inability to comprehensively search and understand the corpus... This is not a failure of search strategy... It is instead a failure to know when to keep looking... agents do not build an effective intermediate model of what the corpus contains."* Their proposed fix: **"allow them to build richer representations of the corpus up front — indexes, summaries, memory — and amortize the cost... across subsequent runs."** (https://www.harvey.ai/blog/legal-agent-bench-law-firm-knowledge). The task/data repo structure itself (`tasks/firm-knowledge/dms/matters/<client>-<matter>/...`, e.g. `1001-00001`) shows the ground-truth is already organized as a client→matter hierarchy (https://github.com/harveyai/harvey-labs/tree/main/tasks/firm-knowledge/dms/matters), which is the natural join key for any schema the agent builds.

## 1. Per-file-type representation (what LLMs consume best)

- **Tables/spreadsheets**: Empirically, format choice matters a lot and plain CSV/JSON are *not* best. A controlled 11-format study found **Markdown-KV (60.7%) > XML (56.0%) > INI (55.7%) > YAML (54.7%) > HTML (53.6%) > JSON (52.3%) > Markdown-Table (51.9%) > Natural-Language (49.6%) > JSONL (45.0%) > CSV (44.3%) > Pipe-Delimited (41.1%)** — CSV/JSONL are the worst commonly-used choices (https://www.improvingagents.com/blog/best-input-data-format-for-llms, Sept 2025). A separate "Table Serialization Kitchen" study found no single best serialization — it's embedding/model-dependent — but that **adding metadata (column descriptions, provenance) to the serialization improves retrieval significantly** (Daniel Gomm, Mar 2025, https://danielgomm.github.io, citing TARGET NeurIPS'24 table-retrieval benchmark).
- **SpreadsheetLLM** (Microsoft, arXiv:2407.09025, Dong et al. 2024) specifically targets messy real spreadsheets (like matter trackers): it proposes **SheetCompressor** — structural-anchor-based compression, inverted-index translation (cell→value mapping instead of raw grid), and data-format-aware aggregation — giving large gains over naive markdown/CSV dumps on large, irregular sheets. This directly matches C&H's .xlsx trackers/analyses.
- **TableRAG** (arXiv:2410.04739, NeurIPS-workshop 2024) shows that for *large* tables (the regime relevant to firm-wide matter/billing trackers), dumping the whole table is infeasible; instead **separate schema retrieval + cell retrieval** (treat columns and cell-values as independently retrievable, embed them, then recompose only the relevant slice) beats program-aided/whole-table baselines and is the SOTA for million-token tables.
- **Chain-of-Table** (arXiv:2401.04398, Google, 2024) shows that letting the LLM iteratively operate on the table (`add_column`, `select_row`, `group_by`, etc., executed programmatically) and feeding back the intermediate *table* — not free text — as reasoning context improves WikiTQ/TabFact/FeTaQA accuracy versus plain CoT. This is relevant for aggregation sub-questions like "every antitrust matter where HSR 2nd request was filed."
- **Word documents / memos / pleadings**: Docling (IBM, arXiv:2501.17887, Jan 2025) and Unstructured are the two leading open-source parsers; Docling produces a unified layout-aware structured representation (preserving headings, tables, reading order) from DOCX/PDF/PPTX and is explicitly positioned as a RAG-preprocessing backbone with LlamaIndex/LangChain integrations. Comparative guidance (https://ghtrends.dev/docling-project/docling/) summarizes: **Docling = layout-fidelity/local processing winner; Unstructured = ETL-pipeline/enterprise ingest; MarkItDown = fast, low-fidelity office→Markdown conversion, no layout intelligence.** For heading-aware chunking of memos/agreements (which is what the Harvey tasks need — pulling clauses, dates, named parties), Docling/Unstructured's structural (not fixed-size) chunking is preferred because it keeps clause/section boundaries, which markitdown's flat text loses.
- **Emails (.eml)**: no single widely-cited 2024-2026 paper standardizes email-thread parsing for RAG, but the consistent engineering practice (per Docling/Unstructured docs and enterprise RAG blog posts) is to parse into a normalized record: `{message_id, thread_id, from, to/cc, date, subject, in_reply_to, quoted_ancestors[], attachments[]}`, de-duplicating quoted trailing text and treating each attachment as a child document linked by `parent_message_id` — i.e., **flatten the thread into a DAG, not raw MIME text**, so retrieval can target the newest message or the full thread as a unit.
- **Slide decks (.pptx)**: handled by the same Docling/Unstructured layout pipeline (slide → title + body + speaker notes + table/image captions), generally the weakest-represented file type in current literature — no slide-specific serialization paper was found; practice is to treat each slide as a chunk with slide-number + deck-title metadata.

## 2. Legal-domain metadata ontologies and extraction targets

- **SALI LMSS (Legal Matter Specification Standard)**: an OWL ontology with **18,000+ stable-IRI tags** covering matter/practice-area/document-type taxonomies, maintained at https://github.com/sali-legal/LMSS and documented at https://lmss.io/specification/. This is the industry-standard controlled vocabulary for exactly the "practice area," "matter type," and "document type" fields C&H needs (antitrust, HSR, M&A, etc.) — using LMSS IRIs as canonical tags (rather than free-text labels) would let an agent's `list_matters(filter=...)` do exact-match filtering instead of fuzzy text search.
- **iManage / NetDocuments profile metadata**: real-world law-firm DMS systems attach a mandatory "document profile" to every file — iManage Control Center's **Metadata/Custom Fields** (Client, Matter, Author, Document Type, Date) (https://docs.imanage.com/cc-help/10.5.3/en-US/Metadata___.html) and NetDocuments' **Profile Attributes** (Client, Matter, Author, and firm-defined custom attributes) (https://support.netdocuments.com/s/article/205220280). This confirms the minimal real-world per-document schema an agent-facing index should replicate: `client_id, matter_id, doc_type, author, date_created/filed, practice_area`.
- **LegalBench-RAG** (Pipitone & Houir Alami, arXiv:2408.10343, 2024; repo https://github.com/zeroentropy-ai/legalbenchrag) is the standard retrieval-only legal benchmark built from CUAD, ContractNLI, MAUD, PrivacyQA — ground truth is (file_path, char_range) spans, evaluated with **Precision@k / Recall@k**, which is directly analogous to the "file existence/quote matching" check needed for C&H's precision criterion.
- **CUAD** (Hendrycks et al. 2021, cited in LegalBench-RAG) defines 41 contract-clause categories (parties, effective date, expiration, renewal, governing law, non-compete, exclusivity, change-of-control, etc.) — this is the template for **contract-element extraction fields** relevant to C&H's "escrow %, non-compete duration" style atomic criteria; these are exactly the kind of fields that should be pre-extracted into a per-document "fact card" rather than re-derived per task.
- **Matter-level fields that matter for C&H-style questions** (synthesized from LMSS + iManage/NetDocuments + CUAD + the blog's own description of "narrow facts" like "a 10% escrow or a two-year non-compete"): `client, matter_id, practice_area, matter_type (e.g., HSR second request), parties/counterparties, deal_type, regulatory_events (filing dates, clearance/second-request dates), outcome (dismissed/settled/cleared), key_dates, key_terms (escrow %, non-compete duration, indemnity cap), status, related_precedent_matters`.

## 3. Structured representations for aggregation/enumeration across a corpus

This is the crux of the Harvey finding (stopping-criterion / enumeration failure), and the literature converges on **"extract-then-query" / structured intermediate representations** over "search-until-satisfied" agentic RAG:

- **Evaporate** (Arora et al., Stanford, arXiv:2304.09433, updated through 2025) is the foundational "LLM-built structured view over a heterogeneous document lake" system: it automatically infers a schema and materializes a **queryable table** from messy documents, trading code-synthesis extraction (cheap, generalizes across docs) vs. direct-extraction (per-doc, costly but precise) — exactly the "document cards queried with SQL" pattern suggested for C&H's matter/document inventory.
- **DocETL** (Shankar & Parameswaran, UC Berkeley, arXiv:2410.12189, Oct 2024) frames the problem as an agentic **query-rewriting + evaluation system for complex document processing pipelines**, decomposing document-level LLM operations (map/reduce/filter over doc sets) with accuracy-aware plan rewriting — a closer analogue to "for every matter, check antitrust+HSR-second-request, then enumerate," because it explicitly optimizes for **recall across a full corpus pass**, not single-query retrieval.
- **LOTUS / Semantic Operators** (Patel et al., arXiv:2407.11418) and **Palimpzest** (Liu et al., MIT, arXiv:2405.14696, "A Declarative System for Optimizing AI Workloads") both propose a **declarative relational algebra over unstructured records** (map/filter/join/sort implemented via LLM calls, optimizer picks model/cost tradeoffs). Both report large accuracy/cost/speed wins over naive per-query LLM calls specifically on **"find all X" / filter-join style workloads** — structurally identical to "pull every antitrust matter with an HSR second request."
- **RAPTOR** (Sarthi et al., Stanford, arXiv:2401.18059, Jan 2024): builds a recursive tree of chunk clusters + LLM summaries at each level, enabling retrieval at variable abstraction levels; reported to improve QA accuracy especially for questions requiring **synthesis across multiple docs/sections** vs. flat-chunk RAG — supports the "hierarchical summaries per matter / per client" recommendation.
- **GraphRAG-family** (GraphRAG, LightRAG, HippoRAG, HippoRAG2) — the **GraphRAG-Bench** meta-study (ICLR'26, arXiv:2506.05690, https://github.com/GraphRAG-Bench/GraphRAG-Benchmark) explicitly finds **"GraphRAG frequently underperforms vanilla RAG on many real-world tasks"** and sets out to identify *when* graphs help: results show graph structure gives the largest gains on **hierarchical knowledge retrieval and multi-hop/complex reasoning**, but not uniformly on fact retrieval — i.e., graphs are not a silver bullet for simple enumeration, but do help when matters/entities interrelate (e.g., counterparty appears across multiple matters). **HippoRAG** (arXiv:2405.14831) builds a schemaless open-IE knowledge graph + Personalized PageRank for associative multi-hop retrieval, strongest on "path-following" multi-hop QA. **LegalGraphRAG** (ACL 2026, https://aclanthology.org/2026.acl-long.1738/) is the most directly relevant: it builds a **hierarchical legal graph** (cases/articles/interpretations at different abstraction levels) plus a multi-agent Researcher→Auditor→Adjudicator pipeline where the **Auditor explicitly verifies each piece of retrieved evidence against source documents before synthesis** — a strong direct precedent for the verification step C&H needs.
- **Long-context/aggregation benchmarks**: **LOFT** (Google DeepMind, "Can Long-Context LMs Subsume Retrieval, RAG, SQL, and More?", ACL Findings 2025, https://github.com/google-deepmind/loft) tests whether long-context models can replace retrieval/RAG/SQL pipelines at up to 1M+ tokens; finding: LCLMs rival retrieval/RAG on single-hop retrieval but **still struggle on compositional/SQL-like multi-hop aggregation reasoning**, i.e. raw long-context stuffing does not solve enumeration — structured retrieval still wins for aggregation. **ListQA** (2026, https://listqa.github.io/) is a dedicated benchmark for exactly the "list/enumerate all X" failure mode seen in C&H: frontier models score **<37% F1** on cross-validated list-formatted factual recall questions, confirming this is a general, unsolved LLM weakness, not specific to legal data or to Harvey's harness.

**Takeaway across #3**: every system that reports strong gains on "find/enumerate all matching records" workloads (Evaporate, DocETL, LOTUS, Palimpzest) does so by **first materializing a structured, queryable intermediate representation (table/graph) offline**, then running exact or near-exact operators (filter/join/count) over it — rather than relying on per-query semantic search to "happen to" surface every match. This is precisely what the Harvey blog recommends.

## 4. Verification approaches

- **FActScore** (Min et al., arXiv:2305.14251, 2023, still the standard reference in 2024-25 follow-ups) decomposes long-form output into **atomic facts** and checks each against a reliable source — directly mirrors the C&H "per atomic rubric criterion" LLM-judge grading, and suggests the agent itself should decompose its draft answer into atomic claims and verify each one against the DMS index before submitting (self-FActScore-style gating), rather than relying on the grader alone to catch omissions.
- **RAGentA** (SIGIR 2025 LiveRAG, arXiv:2506.16988) — multi-agent attributed-QA framework; its hybrid sparse+dense retrieval + dynamic refinement improved Recall@20 by 12.5% and faithfulness by 10.72% over standard RAG baselines, reinforcing that **explicit attribution/verification passes measurably raise recall**, not just precision.
- **LegalGraphRAG's Auditor role** (ACL 2026, above) is the clearest legal-domain precedent for "deterministic check of cited evidence against source documents" — a dedicated agent re-reads the exact cited passage before the Adjudicator finalizes an answer.
- For C&H specifically, the natural deterministic checks are: (a) **file-existence check** — does the cited path/doc_id actually exist in the matter folder; (b) **quote-matching** — does the cited span actually appear verbatim at the cited offset (LegalBench-RAG's own char-span grading methodology is a ready-made implementation pattern); (c) **completeness check against the index** — for every matter/document flagged by the offline metadata table as matching the filter (e.g., practice_area=antitrust AND event=HSR_second_request), confirm the agent's final answer set is a superset/equal set, which converts "enumeration recall" from a search problem into a **set-difference check against a precomputed ground-truth-adjacent index**.

## 5. Concrete recommendation

**Offline indexing pipeline** (build once, amortize across the 250+ tasks — exactly as the Harvey blog urges):
1. **Parse** every file type with a layout-aware parser (Docling for docx/pptx/pdf; a custom `.eml` thread-flattener; SpreadsheetLLM-style compression for xlsx) into normalized Markdown + metadata, not raw bytes.
2. **Extract a three-level schema** into a relational/SQL-queryable store:
   - **Client card**: `client_id, name, industry, client_since, total_matters`.
   - **Matter card** (one row per matter, keyed like the repo's own `client-matter` IDs, e.g. `1001-00001`): `matter_id, client_id, practice_area (SALI LMSS IRI), matter_type, status, parties/counterparties[], deal_type, key_dates{opened, filed, closed}, regulatory_events[] (e.g. HSR filing, second request, clearance), outcome, key_terms{escrow_pct, non_compete_months, indemnity_cap,...}, related_matters[], doc_count`.
   - **Document card** (one row per file): `doc_id, matter_id, file_type, doc_type (CUAD-style clause category or LMSS doc-type tag), author, date, parties_mentioned[], summary (2-3 sentence), section_index (for heading-aware pointer access), source_path`.
3. **Tools exposed to the agent** (mirroring Evaporate/DocETL/Palimpzest's "declarative operator" philosophy and Harvey's "amortized index" suggestion):
   - `list_matters(filter: SQL-like predicate over matter-card fields)` → exhaustive, deterministic enumeration (solves the recall/stopping problem directly, since it's a database query, not a similarity search).
   - `read_doc(doc_id, section|heading)` → heading-aware pointer retrieval instead of full-document dumping (leverages Docling's structural output).
   - `sql(query)` over the matter/document card tables for aggregation questions ("every antitrust matter with an HSR second request") — per TableRAG/Chain-of-Table/DocETL evidence this is the operation class where structured intermediate representations most outperform plain agentic search.
   - `verify(claim, doc_id, span)` → deterministic existence + quote-match check (per LegalBench-RAG's span-grading method and FActScore's atomic-fact-verification pattern) run before final answer submission, to enforce the precision criterion and catch hallucinated citations.
   - Optionally a **matter-relationship graph** (LegalGraphRAG/HippoRAG-style) layered on top of the cards for precedent/cross-matter questions ("what's market standard for X"), since GraphRAG-Bench shows graphs help specifically on hierarchical/multi-hop reasoning, not flat fact lookup.
4. **What the literature values most for this exact failure mode**: converging evidence (Harvey's own diagnosis; LOFT; ListQA; DocETL/Evaporate/Palimpzest/LOTUS) is that **enumeration/recall on "find all X" queries is solved by materializing a structured, SQL-queryable metadata layer offline — not by better embeddings, bigger context windows, or more agentic search steps**. Graph structures (GraphRAG/HippoRAG/LegalGraphRAG) add value mainly for relational/multi-hop reasoning across matters, and atomic-fact/claim verification (FActScore-style) is the standard mechanism to close the precision side once recall is handled structurally.
