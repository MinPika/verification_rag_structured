# Overnight 2026-11-03/04 (x10): what helps? Summary (final)

Haiku 5.5 and Opus 5.5, all 65 tasks, 4 trials per task in every arm. Every difference below is paired over tasks
with a 95% bootstrap CI; * = the CI excludes 0. Full tables (arms incl. strict and N−1 and the test split, all
contrasts, criterion flips, plan recovery, exec usage): [RESULTS.md](RESULTS.md), regenerated by `analyze.py`.
Code: runs/FREEZE_v10_overnight.json for the overnight arms, runs/FREEZE_v10_final.json for A1 text+exec (adds only a
retrieval-mode-correct sentence in the exec note); before the changes: runs/FREEZE_v10_pre.json. 40/40 queue
commands succeeded; one proxy outage (04:53–05:39 UTC) cost two jobs, which were discarded whole and re-run.

## What was tested

| arm | what the agent gets on top of the plain harness | question |
|---|---|---|
| A2 noplan | compiled KB tools + SOP brief, no drafted plan | does dropping the pre-solved plan help? |
| A2 facts (+soft) | the plan replaced by a case fact sheet: facts, SOP block pointers, open questions, no decisions (vrag/facts.py; same author model and inputs as the plan); +soft scopes stop/hold rules to their item | can a non-deciding plan keep the gain without the harm? do over-cautious stops matter? |
| A2 noplan+R, A2 facts+soft+R | the same with the interwhen verifiers (its checklist, pre-call and completion checks) | can the verifiers own the checklist? |
| A1 code+exec | the exec tool: retrieval returns the interwhen baseline's verifier code; policy__verify_action / policy__verify_completion run that registered code on demand; no monitor | does model-invoked code match the monitor? |
| A1 code+exec+fin | + one completion check when the agent finishes | the smallest harness |
| A1 text+exec | the exec tool with SOP text retrieval | keep the SOP text as reading material, add only the checks |
| Opus A1 text / A1 code | retrieval only | diagnostics for Opus |

## Findings

1. **Best configuration for both models: SOP text retrieval + the exec tool; no monitor, no plan.**
   Haiku 84.8: +13.3* mean, +15.4* strict, +16.2* N−1 over the plain agent; +3.5* mean over the monitor (R);
   +6.9* over A2; equal to A2+R (+1.7, n.s.); best N−1 of every Haiku arm (44.6). Opus 87.1: equal to the plain
   agent (−0.4, n.s.), R and A2+R; the best Opus arm, but not above A0. Both models call
   policy__verify_completion unprompted in 99–100% of trials (~2.3 times); Haiku also checks a proposed action in 69% of
   trials (Opus 16%).
   Example (hr_crestwood ee4d1791, an A1 code+exec trial): Haiku drafts "Family and Medical Leave Act (FMLA) Eligibility Notice – Approved —
   Torres, E-1001", calls verify_action, is told the SOP subject format is "[Template Name] — [Last Name], [ID]",
   and sends "FMLA Eligibility Notice – Approved — Torres, E-1001".
2. **the exec tool matches or beats the interwhen monitor without one.** Same registered code: run by the model
   (A1 code+exec) vs run by hooks (R): Haiku +2.8* mean, Opus +0.4 (n.s.). One finish check on top adds nothing
   (Haiku +0.2, Opus −0.1): the agents already ask for the completion check before they finish. Code vs text
   retrieval under the exec tool: Haiku equal; Opus text better (+8.5* N−1).
3. **The verifiers can own the checklist: with them, the plan does not matter.** A2 noplan+R = A2 facts+soft+R =
   A2+R = R for both models (all n.s.). Haiku's gain needs no per-task pre-solving by a frontier model.
4. **Without verifiers, the plan was carrying A2; nothing replaces it.** Dropping it: Haiku −9.1* mean, Opus
   −13.5* strict vs A2. The non-deciding fact sheet equals no plan; soft stops change nothing (Haiku +0.1, Opus −0.1).
   The plan helped Haiku through its decisions, i.e. through Opus pre-solving the task offline.
5. **Why Opus never beats its plain self.**
   - Little headroom: 104 solid failures, of which 35 are verified rubric defects and 14 fail for ≥ 7 of 8 models;
     13 are Opus-specific. Noise is small (A0 half vs half −0.4 [−2.1, +1.2]), so the flat results are real.
   - The KB tools alone cost Opus −6.5* mean, −16.0* N−1 (the brief adds nothing, −0.2): with them Opus opens the
     SOP document in 62% of trials instead of 99% and works from compiled, lossy procedures (Haiku makes the same
     switch at no cost, −0.8).
   - the interwhen verifiers fire as often as for Haiku (0.83 pre-call denials per trial) and fix 30 Opus failures, but
     break 33 criteria Opus passes (Haiku: 84 fixed, 28 broken). 21 break in all four verifier arms; annotated
     (docs/failure_analysis/data/labels_opus_verifier_regressions.jsonl): Opus treats the verifier checklist as the
     complete to-do list and skips what the SOP requires beyond it (10; its read calls halve), wrong verifier spec
     (4), verifier redirects the action (4), rubric defect with the verifier right (3), noise (0).
   Every component replaces part of the model's own SOP reading; that helps a model that reads worse than the
   compiled material (Haiku) and costs one that reads better (Opus).

## What this means for the five ideas

| idea | verdict |
|---|---|
| Do not pre-solve for strong models; plan only as the verifiers' checklist | Supported: with the verifiers the plan adds nothing, so pre-solving can go. For Opus neutral, not a gain. |
| Plan as facts and pointers, no decisions | Does not help (= no plan). |
| Drop the plan | Only with the verifiers or the exec tool; alone it hurts. |
| Stop rules as flags | No effect for Haiku or Opus (the over-caution was mostly gpt-6-sol). |
| Corpus as citable blocks compiled into executable task-resolved code | Supported when the code is executed (exec tool); reading it as the SOP hurts Opus. Tested with the interwhen baseline's specs (code per obligation/prohibition, mapped to K0 blocks); compiling our own specs was not attempted. |
| the exec tool | Works: the best arm for Haiku with SOP text retrieval, no monitor and no plan; neutral for Opus. |

## Next steps suggested by the data

- Opus: run the verifiers without the upfront checklist (pre-call blocks and completion check only) and phrase
  findings as "checks found so far, not the task list"; this targets the main mechanism (10 of 21).
- Exec tool for strong models without KB retrieval at all (plain agent + verify tools), since the KB tools are what
  costs Opus.
- Improve verifier coverage of expected outputs and fix wrong specs (the remaining Haiku failures and the Opus
  regressions point at the same specs).
